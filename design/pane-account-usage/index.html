01 / PLACEMENT

One small progress ring in the header

Place a 16px progress ring in a 28px button immediately before the pane’s overflow menu. The ring fills clockwise with usage. Its normal color matches neighboring buttons; 70% turns amber and 90% red, including on hover. No percentage badge or extra row. The tooltip names the most-used relevant window.

02 / MEANING

Hover to glance, click to inspect

The tooltip says “Account usage · 5-hour limit · 93% used.” Clicking opens an anchored popover with the login, every window and reset times. “View usage” opens the Usage page with this host and verified account selected. The ring stays recognizable: a question mark indicates an unknown login, the same neutral dashed ring marks stale and unsupported usage, with distinct tooltip messages. Keyboard focus also reveals the tooltip.

03 / IDENTITY

Follow the running login

Changing the default account affects future launches. This header control stays attached to the running session. If the login changes or cannot be verified, retain the ring outline and show a status marker without a fabricated percentage.

Identity edge cases and acceptance checks
  • Two panes with the same verified login show identical quota values. Different logins on one host resolve independently; identical profile paths on different hosts never collide.
  • Record the effective login at the agent launch boundary, including explicit environment overrides. A terminal’s initial environment alone is insufficient because wrappers re-resolve defaults on each agent launch.
  • A login slot can be re-signed while an older process is alive. Invalidate attribution on identity changes; confirm through the running harness if available, otherwise show “Login unverified.” A profile path alone cannot prove the process switched accounts.
  • Token refresh can change a credential fingerprint without changing the account. Use a stable provider identity where available; treat a fingerprint change as a reason to revalidate, not as proof of a different person.
  • Manual CLI launches, restored sessions, custom wrappers, remote hosts and native chat harnesses need the same verified binding contract. Fall back to “Login unverified” when that evidence is absent.
  • API-key billing shows no subscription percentage. Missing reset timestamps read “Reset time unavailable.” Provider errors never render as 0% or unlimited.
  • Do not disable sending at 100%: provider-reported extra usage, credits, or other limits may still allow work. No automatic account switching or session restarts.
  • Verify shared query deduplication, login-switch isolation, stale data, 320px panes, keyboard dismissal and screen-reader labels before shipping.

First slice: add verified launch-account attribution for Claude and Codex, then the header progress ring with account details and all fallback states. “View usage” opens the existing Usage settings screen on the session’s host, with the verified account focused. If attribution is unknown, open the provider overview without preselecting an account. Returning restores the original pane. The application implementation is now present in this worktree.
