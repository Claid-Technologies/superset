Competitive scan · companion to the multi-repo projects PRD

Every piece of this exists.
Nobody has assembled it.

Ten tools were checked for how they handle work that spans several repositories. VS Code has shown per-repo diffs since 2017. Capy and Factory isolate every task in its own VM. Codex has a project-level folder list with a primary. DevSwarm has per-repo pull requests. Not one of them has all four at once — and the tools closest to being an agent workspace are the ones furthest from the git surfaces. That gap is the opening, and it decides what our v0 is.

17 Sep 2026 · v2, claims verified Conductor · Cursor · Codex · Kilo · Devin · DevSwarm PRD: docs/prd/multi-repo-projects.md

The finding

Three things the scan settled.

01

The cheap version is now table stakes

"One agent sees N folders, git stays on one repo" is what Conductor, Cursor and Codex all ship today. Building it is days of work and buys no differentiation — but not having it is now a visible gap.

02

Per-repo diffs aren't novel — the editors have had them for years

VS Code's Source Control view groups changes by repository in a multi-root workspace, with independent commits per repo; Cursor and Kilo inherit it. DevSwarm goes further with per-repo PRs, bought with a submodule bundle. What's missing everywhere is pairing that with a project-owned repo list and real isolation.

03

Their isolation is a half-truth

Codex worktrees cover the primary repo only; secondaries are shared directories that parallel threads trample. Conductor links live worktrees another agent may be driving. We already have the machinery to not do this.

Four things called "multi-repo"

Most of the disagreement in this space is a vocabulary problem.

Nine tools now claim multi-repo support and they mean four different things. Sorting them first makes the rest of the page smaller, and it's why the matrix below only covers tiers 2 and 3 — comparing a tier-1 tool on "per-repo diff" scores it ○ for a capability it never set out to have.

1

Multi-repo access — one task, one repo

The agent is entitled to many repositories; any individual task still targets one. Capy: you pick repos when installing the GitHub App, then each task gets its own branch capy/<task-slug>-<id> and its own PR. Devin bulk-indexes repos and groups sessions by target repository. Useful, and not the problem this PRD is about.

2

Multi-repo context — one agent sees N folders, git owns one

Where almost everyone is: VS Code multi-root (the original), Cursor (inherits it), Codex (primary folder + secondaries), Conductor (/add-dir), Kilo (projects in one panel). The agent reads and writes across folders; every git surface stays anchored to one repo.

3

Multi-repo workspace — N checkouts, per-repo git surfaces

DevSwarm, alone, via a submodule bundle. This is the tier the PRD is aiming at and where our cut 2 lands.

4

Coordinated fan-out — N agents, one per repo, N PRs

Factory Missions: "run coordinated changes across dozens of repositories… decompose large projects into independent subtasks and assign each to a dedicated Droid." Orthogonal to a shared workspace — it's the answer when the change is mechanical and repeats across many repos, not when one feature threads through three. Worth knowing we could reach it later by pointing automations at a project.

The row that changed the conclusion is VS Code's. Its Source Control view has grouped changes by repository in a multi-root workspace for years, with independent commits per repo — so "per-repo diff" is not novel, and Cursor and Kilo inherit it for free by being VS Code. What none of the ten has is the combination: a project-owned repo list, isolation per workspace, per-repo diffs and a per-repo ship surface in one product. Every individual capability exists somewhere; the assembly doesn't.

Tool by tool

What each one actually does, in their words.

Conductor

links workspaces

one repo per workspace · /add-dir

"Add each directory to Conductor… Create a workspace for each directory… In one workspace, enter /add-dir and select the other workspaces you'd like to link together."

Workspaces live at ~/conductor/workspaces/<repo name>/<workspace name> — one worktree, one branch, one diff viewer. Multi-repo is Claude Code's own --add-dir flag surfaced as a slash command. Their recommended answer to multi-repo is actually "use a monorepo": "Conductor supports monorepos out of the box."

Gap: N sidebar rows per task, uncoordinated branch names, edits to a linked repo land in that other workspace's diff viewer — and per Anthropic's docs, --add-dir loads none of the linked repo's CLAUDE.md by default.

Cursor

multi-root editor

VS Code .code-workspace · Apr 2026

"A single agent session can now target a reusable workspace made of multiple folders."

Inherited straight from VS Code: a workspace file lists folder roots, indexing runs per root, @Codebase spans them. Genuinely good for context. Git stays per-folder and the workspace file is yours to maintain by hand.

Gap: no project-level definition, no isolation, no git story beyond what VS Code already gave you.

Codex

primary-folder anchor

multi-folder projects · 23 Jul 2026, build 26.715

"New chats, Git operations, and discovery of AGENTS.md, skills and config.toml use the primary folder; secondary folders remain available for file search, reading, and editing."

The closest to our design: a project is an ordered folder list with one marked Primary, and the primary owns every git surface. Secondaries are plain existing directories — not worktrees — shared across every thread, with .git/ read-only and the diff panel scoped to the primary cwd.

Gap: worktree mode forks the primary only, so two parallel threads edit the same secondary directory. #35260 — hand-made sibling worktrees don't even reach the sandbox's writable roots. Open, no reply.

Kilo

projects in a panel

Multi-project Agent Manager · experimental, off by default

"Each repository has its own worktrees, sessions, sections, selection and state… so sessions and worktrees are not mixed between repositories."

Explicitly not a unified workspace — several repos shown as separate projects in one panel, each with state in its own .kilo/agent-manager.json. A maintainer has filed to formally forbid pointing it at a non-git parent folder, because users keep trying and Agent Manager mishandles it.

Gap: grouping, not unification. One agent never spans two repos.

Devin

indexing + grouping

multi-root virtual FS · thinnest evidence of the six

Their changelog confirms "support for working on multi-root workspaces containing virtual filesystem folders," plus bulk repo indexing and sessions groupable by target repository. The visible investment is in knowing about many repos, not in checking several out together.

Unknown: no public documentation of a project repo list, shared branch or per-repo ship flow — treat the empty cells as unevidenced, not as confirmed absences.

DevSwarm

closest to the ambition

git submodules + worktrees

"Every repository inside a Multi-Repo is backed by Git submodules… each member is checked out as a Git worktree that shares the underlying repo's object store instead of creating another full clone."

The only product with the full shape, and the mechanics are specific enough to believe: "each repository keeps its own history, its own remote, its own branches, its own pull requests." The review surface is real too — "the unified file list shows every repo's diff in one place. Filter to the api member to scrutinize the contract change on its own."

Caveat: vendor documentation, not verified hands-on — and whether all members share one branch name is never stated. Submodules impose a parent repo and ongoing SHA maintenance, which is the tax we should be able to avoid.

Why they all stop

The hard part isn't the checkouts. It's everything keyed by one workspace.

Cutting N worktrees is easy. What's expensive is that a single-repo product accumulates state keyed by workspace, on the safe assumption that a workspace is one repo — and that the agent quietly assumes it too. Five such places were found: three in our code, two in Claude Code's documented behaviour. The last two are the ones the PRD doesn't mention and are the reason the container folder isn't free.

1

The host-service status cache would serve the wrong repo's diff

Keyed Map<workspaceId, Map<baseBranch, Variant>>. Three repos in one workspace usually share a base branch name, so they collide on one key and the last snapshot wins. Silent wrong data, not a slowdown.

Scope, now verified: this is the host-service git router, which serves remote and cloud workspaces. The desktop's own Changes surface is a separate, fully path-based router — worktreePath: z.string(), validated against a registered-worktrees table, cached by makeStatusCacheKey(worktreePath, branch). For a local workspace the switcher never touches this cache at all.

git-status-store.ts:31 · desktop changes/status.ts:25

2

The refresh queue would serialize the repos

Map<workspaceId, WorkspaceQueue> with one active slot and a FIFO queue — three repos refresh one after another. Fixed by the same change as above: key on workspaceId + repoFolder.

git-status-refresh-limiter.ts:31

3

Only one checkout would be watched

One { workspaceId, worktreePath, watcher } per workspace, attached from the row's single path. Without N watcher pairs plus refcounting, edits in the other repos never mark the workspace dirty. The fiddliest of the four.

git-watcher.ts

4

Every repo's AGENTS.md would go lazy

Anthropic's docs, verbatim: "Claude also discovers CLAUDE.md and CLAUDE.local.md files in subdirectories under your current working directory. Instead of loading them at launch, they are included when Claude reads files in those subdirectories."

So opening the agent at a container folder demotes each repo's instructions from eager to lazy — on this repo, that means starting without the i18n, comments and plugin rules until something happens to touch a file. Codex has the identical problem and documents it. Conductor's /add-dir route is worse still: those directories' CLAUDE.md files are not loaded at all unless CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD is set.

mitigation: WS-6 root manifest, now mandatory rather than nice-to-have

5

Auto memory would fragment per workspace

Also from Anthropic's docs: the auto-memory directory "is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead."

A container folder is not a git repo, and its path is per-workspace. So every multi-repo workspace would get its own empty memory directory instead of sharing the repo's — and lose it on delete. Today every worktree of a repo shares one. This is a silent regression in agent quality that no test would catch.

mitigation: set CLAUDE_CODE_PROJECT_DIR_NAME at agent launch (needs Claude Code ≥ v2.1.234)

The good news is the diff plumbing itself is contained. Every host-service git procedure resolves its path through one 31-line function, called from 24 sites — 21 of them in a single file — all shaped identically. A repo switcher is an optional second argument, not a rewrite. That matters because redefining the workspace path itself would touch 1,756 non-test references, and refusing that one change is what keeps everything else cheap.

Where we land

Two anchors instead of one is the whole trick.

Codex anchors git at the primary folder because it has one anchor to spend. Kilo's maintainer wants to forbid non-git parent folders for the same reason: their workspace root doubles as the git root, so pointing it at a container breaks worktrees and setup scripts. Splitting the two fields dissolves the tension. 

~/.superset/worktrees/<primaryProjectId>/avi/multi-repo/   ← rootPath: agent, terminal, file tree
  superset/       .git → file into base repo   branch: avi/multi-repo   base: main   ← worktreePath
  skills/         .git → file into base repo   branch: avi/multi-repo   base: main
  homebrew-tap/   .git → file into base repo   branch: avi/multi-repo   base: master

worktreePath

git anchor
  • Always a real repository checkout — Kilo's objection never applies
  • Stays the primary, so all 1,702 references keep working untouched
  • Changes, Ship, PR status, status refresh: unchanged in v0

rootPath

human + agent anchor
  • The container folder the person opens
  • Repos are children of cwd, so no --add-dir, no sandbox roots
  • Never passed to git, setup scripts or worktree operations — one-line invariant, cheap test

The resulting position: Codex's UX and its cheap git story, plus the per-repo isolation Codex and Conductor both lack, plus a real branch in every repo — which turns per-repo PRs from a redesign into an increment.

Individual developers keep hand-rolling this container as the "meta-repo" or "repo-of-repos" pattern because it's the only way to get an agent that sees everything. No product ships it. That gap is the opening.

What v0 is

Host-side only. No cloud schema change at all.

superset ws create --project already takes local project ids, and a local project already means "one repo checked out at one path." So the Source-folders dialog is a picker over things we already have — which deletes the most expensive requirements in the PRD outright.

In

~8 of 62 requirements
  • Source-folders list on the project, first is Primary (Codex's dialog, simplified)
  • One checkout per repo, isolated per workspace — worktrees on a device, the sandbox itself in cloud (WS-1)
  • Same branch name in each repo where it's free, bumped per repo where it isn't (WS-2, downgraded — see open questions)
  • Atomic create with rollback (WS-5)
  • Agent context kit: root manifest + SUPERSET_WORKSPACE_REPOS + CLAUDE_CODE_PROJECT_DIR_NAME (WS-6 — mandatory, see landmines 4 & 5)
  • Delete removes every worktree, then the root (WS-9)
  • Missing repos cloned on first use (WS-4)
  • Repeatable --project, repos array in ws get (CLI-2, CLI-4)

Out

deferred or deleted
  • GitHub App Add-repositories dialog (PRJ-2 — deleted, not deferred)
  • Per-repository installation tokens (SEC-1 — folders are already cloned)
  • project_repositories in Postgres + migration (MIG-1)
  • Cloud sandboxes, environments, warm snapshots (all of §8.3)
  • Sidebar grouping by project (WS-8 — falls back to primary)
  • Per-repo setup scripts (WS-7)

Then, immediately: the part only DevSwarm has

PR-1 (repo switcher on Changes) and PR-2 (one PR per repo against its own base). Both the Changes view and the file tree hang off a single variable each — ChangesContent.tsx:22 and FilesView.tsx:149 — so the client side is small.

The open question from v1 of this page is now answered, and it's good news: the desktop's changes router is path-based end to end, keyed by worktreePath and validated against a registered-worktrees table. So for local workspaces, cut 2 is "register N worktree paths, pass the selected one" and landmines 1–2 never fire. They still have to be paid for remote and cloud workspaces served by the host-service router, and landmine 3 (one watcher per workspace) is unavoidable either way.

The verdict

Three cuts. The agent-context work is not optional in any of them.

Build the host-side primitive first and the cloud project side last — the inverse of the PRD's milestone order. The PRD builds the web project flow (M3) first, which front-loads the GitHub App dialog, a Postgres table and a migration. None of that is needed to make multiple repositories feel native, because ws create --project already takes local project ids.

Cut 1 — v0, days not weeks

Source-folders list over local projects with a Primary. One isolated checkout per repo, atomic create, delete-all. rootPath opens the agent and the file tree; worktreePath stays the primary and owns every git surface, so all 1,756 references keep working. Plus the agent context kit — root manifest, SUPERSET_WORKSPACE_REPOS, CLAUDE_CODE_PROJECT_DIR_NAME — which landmines 4 and 5 promoted from polish to prerequisite. Ships strictly ahead of Conductor and Codex on isolation, level on everything else.

Cut 2 — the differentiator

Repo switcher on Changes, then a Ship surface that lists each repo with commits ahead and opens a PR for the ones you check — against that repo's own base. Not "one action fires N PRs": you pick. Cheap for local workspaces now that the desktop router is confirmed path-based; the host-service cache and limiter get keyed by workspaceId + repoFolder for remote, and the watcher becomes N pairs. Note this is not novel UX — VS Code has grouped changes by repository for years, so the pattern is well-trodden and the risk is low. What's novel is having it together with a project-owned list and per-workspace isolation. Cross-linked PR bodies and workspace-name titles (PR-3) are the opinionated part and stay out until someone asks.

Cut 3 — cloud

Exactly as the PRD stages it (§8.3, ENV-*). No competitive pressure here — not one of the six ties multi-repo to a cloud environment model, so this is ours to schedule.

Four things to explicitly not do

  • Don't redefine worktreePath as the container. 1,756 references, and it buys nothing cut 1 doesn't already give.
  • Don't use submodules. DevSwarm's bundle works but imposes a parent repo and SHA maintenance; a project-owned repo list gets the same result with no git-level coupling.
  • Don't build the GitHub App repo dialog for v0. PRJ-2 and SEC-1 are deleted by the local-projects picker, not deferred by it.
  • Never pass rootPath to git, setup scripts or worktree operations. One-line invariant, one cheap test — and the exact conflation a Kilo maintainer has an open issue to prevent.

The one thing to check before committing

A DevSwarm trial. Everything above assumes we can reach their capability without their submodule tax. That assumption is load-bearing for cut 2 and it has not been tested.

Open, from review

Three challenges from Avi on v2, two of which moved the plan:

  • Worktrees shouldn't be enforced regardless of environment. Agreed, and the matrix row is reworded to say so. The requirement is the outcome — no two workspaces share a checkout — not the mechanism. On a device a worktree delivers it; in a cloud sandbox the sandbox already is the boundary, so plain clones under /workspace are correct and cheaper. The PRD already splits it this way (ENV-3); v1 of this page flattened it.
  • Is one branch name across repos necessary? No. Downgraded from a constraint to a convenience. WS-2's "if the name is taken in any repo, bump it in all" needs a probe of every member before create and produces a surprising rename; per-repo bumping gives matching names almost always and breaks nothing when it doesn't. Cross-links live in PR bodies, not in a branch-name search, so nothing downstream depends on it.
  • "One PR per repo from one action" feels opinionated. Fair, and it was my phrasing overselling it — the PRD's PR-2 was already opt-in per repo. Reworded to "Ship surface knows about N repos; you pick which to open." The genuinely opinionated pieces (cross-linked bodies, workspace-name titles) are now explicitly out of scope.

Evidence quality

Every quote on this page was re-checked against its primary source for v2. What changed:

  • One quote was wrong and is gone. v1 attributed "A workspace is tied to exactly one repository" to Conductor. That sentence does not appear in their documentation — it was a summarisation artifact. The substance holds and is now carried by their actual words ("create a workspace for each directory… then /add-dir") plus the repo-keyed workspace path.
  • Two numbers were wrong and are corrected. 33 resolveWorktreePath "call sites" was really 33 references including imports and type positions; there are 24 actual calls. And worktreePath non-test references are 1,756, not 1,702 — v1 used a filter that also dropped lines merely containing the word "test".
  • DevSwarm was under-claimed. v1 marked their per-repo diff "claimed, not verified". Their own documentation is specific and mechanical — submodules, worktrees sharing an object store, a unified file list filterable per member — so the row is upgraded. Still vendor documentation, still no hands-on trial.
  • Verified verbatim: the Cursor sentence, both Kilo sentences, the Codex release note (build 26.715, 23 Jul 2026), and the Conductor three-step. Codex's read-only .git/ is corroborated by several independent openai/codex issues and is a general sandbox behaviour, not specific to secondary folders.
  • Devin remains the thinnest row. Multi-root support is confirmed from their changelog; everything else is absence of evidence, and the matrix now says so rather than scoring it.

Highest-value remaining check: 30 minutes in a DevSwarm trial. They are the only competitor with the capability this plan treats as the differentiator, and whether their submodule bundle is load-bearing or incidental changes how confident we should be that we can beat it without one.
