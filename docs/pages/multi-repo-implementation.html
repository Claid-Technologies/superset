Implementation · multi-repo projects · v1

Codex's model, with one difference
that changes what it's worth.

A project becomes a primary folder plus any number of additional folders. Codex ships exactly this and gives the primary a worktree, leaving the rest as shared directories two threads can trample. We give every folder its own checkout — the difference between "the agent can see your other repo" and "this workspace owns its own copy of all three."

The requirement is that outcome, not the mechanism. On a device a git worktree delivers it. In a cloud sandbox the sandbox is already the isolation boundary, so plain clones under /workspace are correct there and worktrees buy nothing. This page is the device cut; read "worktree" below as "the device mechanism for one isolated checkout."

The shape

One container, N checkouts, one branch name, git anchored on the primary.

On a device — worktrees

~/.superset/worktrees/<primaryProjectId>/avi/multi-repo/      ← the container
  superset/        worktree · branch avi/multi-repo · base main    ← primary · agent cwd · workspaces.worktreePath
  skills/          worktree · branch avi/multi-repo · base main
  homebrew-tap/    worktree · branch avi/multi-repo · base master

Each folder is a real git worktree cut from its own base repo, so their .git files point into three unrelated repositories and none of them knows the others exist. The container is a plain directory with no git in it. Nothing is a submodule and there is no parent repo.

In a cloud sandbox — the folders, on a branch

/workspace/                                                   ← the container, one sandbox per workspace
  superset/        clone · checked out on avi/multi-repo          ← primary · agent cwd
  skills/          clone · checked out on avi/multi-repo
  homebrew-tap/    clone · checked out on avi/multi-repo

Same container, same folders, same branch name — and no worktree anywhere. Put each repo in its folder and git checkout -b. The next section is why that is not a shortcut but the correct answer, and what drops out of the build because of it.

The load-bearing decision: workspaces.worktreePath keeps pointing at the primary checkout, not the container — a worktree on a device, a clone in a sandbox. Either way it is still a git checkout, so every one of the 1,756 non-test references to it keeps working untouched: Changes, Ship, PR status, status refresh, delete. Multi-repo becomes additive instead of a rewrite.

Local and cloud

One model, two provisioning paths — and the cloud one is much shorter.

git worktree solves a problem only a device has: many working copies of one repo on one machine. A sandbox holds exactly one workspace and therefore exactly one working copy per repo, so the feature has no job there. Using it anyway would mean inventing a base repo to cut worktrees from, purely to preserve a symmetry nothing benefits from.

Everything above provisioning is shared, and that is what makes the split safe: the container with N folders, the folder list copied at creation, one branch name, the primary at position 0 owning the git surfaces, workspace_repos, the host-service rows the sandbox seeds for itself, the folder picker, and the agent launch. The two paths differ only in how a folder becomes a working copy.

StepDeviceCloud sandbox

Make the working copy git worktree add from the base repo into the container Nothing — the clone is the working copy
Get on the branch Part of worktree add -b, after checking the name is not already held by another worktree of that repo git checkout -b in the folder
Branch collisions Real. The name may exist, or be held by another worktree — including a stale registration whose directory is gone, which is why creation prunes first None locally. The sandbox is fresh, so only the remote can collide, and that surfaces at push
Delete Dirty-check each folder, delete the branches, git worktree remove each, remove the container, keep each base repo's worktree list honest Destroy the sandbox
Failure modes to handle Stale worktree registrations, "branch is already used by worktree at <missing-path>", partial rollback across N folders, the rm -rf guard resolving against the right project id Clone failures on a cold start. That is the list

What this means for the build

Read the table right to left and the useful conclusion falls out: almost every hard part of this plan is device-only. Atomic rollback across N folders, the branch-collision pass, the delete saga and its safety guard, resolving folders to existing local projects — none of it exists in the cloud path. The device path is carrying the complexity, and it is the one we are building first anyway.

So cloud should land as a genuinely small addition on a shared model, not a second implementation. The thing to protect is that split: one branch, in one step (step 4 below), and no "is cloud" flag threaded through resolution, branch naming, registration, rollback or delete. If that flag starts spreading, the two paths have begun to diverge and the shared model is no longer real.

The one thing cloud makes harder, not easier. Worktrees make N folders nearly free on disk; clones do not. A three-repo workspace in a sandbox is three full checkouts plus three sets of dependencies, against a writable disk that is half the environment's memory. That is why environment size, warm snapshots and a cap on folders per project are cloud concerns — on a device they barely register.

Where we diverge from Codex

They mount folders. We check them out.

 Codex multi-folder projectsThis plan
Primary folder Git root; drives chats, git ops, AGENTS.md discovery Same
Additional folders Existing directories mounted as-is, .git/ read-only An isolated checkout each, on the workspace's branch — worktree on a device, clone in a sandbox
Parallel work Two threads edit the same secondary directory and trample each other Every workspace owns its checkouts; nothing is shared
Branch in a secondary None — whatever the folder happened to be on The workspace's branch, so commits land somewhere meaningful
Shipping a secondary "Each repository must be committed independently", outside the app A real branch exists, so per-repo PRs become an increment, not a redesign

That last row is the point. Codex's secondaries have nowhere for a commit to go, so per-repo pull requests would need a redesign before they could even start. Ours have a branch from day one, which is what makes the Ship surface a later increment rather than a different product.

Data model

What the mapping is today, and the smallest change that makes it a list.

How a project maps to a repo today

There is no mapping table. The mapping is a column, and it lives in three places that are mid-migration — which is the single most important thing to know before adding anything.

And there is no link column between them

Nothing on a host project stores a cloud project id. When the two have to be associated, it happens by matching the git remote URL at lookup time through v2Project.findByGitHubRemote — and even that only runs on the v1 importer path. Meanwhile v2_workspaces.project_id is now written with the host-side local project id, which is exactly why its foreign key could be dropped.

Which settles where the folder list goes. An earlier version of this page put it in the cloud, hanging off v2_projects. That was wrong — you cannot add a table to one that is being deleted. The project definition has already moved host-side, so the folder list follows it: project_folders in host.db, beside the table that already owns repo_path.

This makes the plan simpler, not harder. Multi-repo becomes entirely host-side — no Postgres migration, no cloud schema change — which is consistent with ws create --project already taking a local project id.

Host — the project's folder list

A project keeps its own columns and gains rows. An existing project gets exactly one row mirroring repo_path, so a single-repo project is a multi-repo project with N=1.

A prior-art note, not a shortcut

local-db's worktrees table is already { id, projectId, path, branch, baseBranch, gitStatus, … } — one row per checkout, keyed by project, with no assumption that a workspace has only one. Worth reading as precedent for the workspace_repos shape.

It is not something we can build on, though: that table belongs to the v1 desktop store this repo is migrating away from. An earlier draft of this page claimed the folder picker got its registry and its path validation from it for free. It does not.

Projects v2, behind a flag

A new creation path. The old one keeps working untouched.

The flag is a PostHog gate registered in FEATURE_FLAGS (packages/shared/src/constants.ts:105) and read with useFeatureFlagEnabled(FEATURE_FLAGS.MULTI_REPO_PROJECTS), matching how CLOUD_ACCESS and V1_AUTO_MIGRATION already work.

"v2" here means the second version of the project shape, and is unrelated to the v1→v2 desktop migration V1_AUTO_MIGRATION paces. Worth picking different words before this ships — the collision will cost someone an afternoon otherwise.

What the flag actually gates

  • On: the project form shows a Source folders list — add a folder, remove one, mark one primary. Workspaces created in a project with 2+ folders get the multi-repo path.
  • Off: the form is exactly what it is today. One folder, no list, no picker.

Backward compatibility, stated as rules

  1. One folder is not a special case, it is the general case with N=1. A project with a single folder produces a workspace with root_path = NULL and one workspace_repos row whose worktree_path equals worktreePath. Byte-for-byte what exists today.
  2. No folder moves on disk. Existing workspaces are never restructured into a container. Only workspaces created after the flag, in a project with 2+ folders, get one.
  3. Old clients ignore the new fields. root_path and the repos array are additive; a pre-change desktop reads worktreePath and behaves as before, which is why the primary had to stay there.
  4. The migration is a backfill, not a rewrite. One workspace_repos row per existing workspace, idempotent, derived from columns that already exist.

The invariant to enforce with a test: root_path is never passed to git, to a setup script, or to a worktree operation. It is a display and launch path only. Kilo has an open issue from a maintainer asking for exactly this guard, because their workspace root doubles as their git root and pointing it at a non-git folder breaks worktrees and setup scripts. Our two fields keep that impossible — as long as nothing crosses them.

Creating the workspace

A loop, a shared branch name, and a rollback that leaves nothing behind.

  1. Resolve the folder list

    Copy the project's folders onto the workspace at creation time. Editing the project later changes future workspaces only; a live workspace never changes shape.

  2. Resolve each folder to a local project — device only

    Match by explicit link, then by remote URL, otherwise clone to ~/.superset/repos/<owner>/<name> and create the local project. Progress streams into the workspace's setup terminal so a cold first run is visible rather than a hang.

    A sandbox skips this entirely — there are no pre-existing local projects to match against, so the clone in step 4 is both the fetch and the working copy.

  3. Pick the branch name

    Use the same name in every repo where it is free, and bump only the repo where it is taken. Names match in the ordinary case; nothing breaks when they don't. Cross-links live in PR bodies, so nothing downstream depends on the names being identical.

  4. Create the container, then N checkouts

    mkdir the container, then materialise each folder, primary first. Base branch comes from each folder's row, so homebrew-tap can fork from master while the others fork from main.

    This is the only step that differs by environment, and it should stay that way. A device runs git worktree add -b against the local base repo. A sandbox runs git clone then git checkout -b — or a shallow fetch, against a warm snapshot. Everything before and after is identical, so confining the branch here is what stops the two paths diverging later.

  5. Register and persist

    Insert the workspaces row with root_path set, N workspace_repos rows, and N rows in the desktop's worktrees registry so the Changes pane will accept each path.

  6. Roll back as a unit

    If any worktree fails, remove the ones already created, delete the container, and surface an error naming the folder that failed. A half-built multi-repo workspace is worse than none.

Delete is the same loop, reversed — on a device

List the folders, refuse if any is dirty and name it, apply "delete branch" to all of them, git worktree remove each, then remove the container. The existing rm -rf safety guard checks a path is inside the project's managed worktrees root — it needs to take the primary's project id, since the secondaries' worktrees live under the primary's tree and would otherwise fail the check and silently refuse to clean up.

In a sandbox none of this exists. Destroying the sandbox destroys every checkout at once: no dirty gate, no per-folder removal, no container cleanup, no base-repo worktree lists left to keep honest. The dirty check is still worth offering as a warning before destroy, but it is a courtesy there rather than a correctness requirement.

Launching the agent

In the primary, not the container — and that decision pays for itself.

The agent's cwd is the primary worktree. The spawn procedure already takes an optional cwd (terminal-agents.ts:545), so this is a value, not new plumbing. Two things fall out, and they are the reason this is the right call:

The primary's instructions load eagerly

landmine avoided
  • Claude Code loads CLAUDE.md from cwd and every directory above it at launch
  • Files in subdirectories load only when it reads inside them
  • cwd = primary means the primary's CLAUDE.md is in context from the first token

Auto memory stays where it belongs

landmine avoided
  • The memory directory is derived from the git repository; outside a git repo it falls back to the project root
  • A container is not a git repo and its path is per-workspace — so launching there would give every workspace its own empty memory, discarded on delete
  • cwd = primary keeps one memory directory shared across all worktrees of that repo, as today

The cost, stated plainly: the other folders are now siblings of cwd, not children, so the agent cannot reach them by default. Launch has to pass each secondary as an additional directory, and Anthropic's docs are explicit that those directories' CLAUDE.md files are not loaded unless CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 is set — so we set it.

This is a trade, not a free win. Launching at the container would have made the folders children and skipped the flag entirely, at the price of both landmines above. Fragmented auto memory is the worse outcome: it degrades agent quality silently and no test would catch it. Worth knowing that additional-directory permission handling has rough edges in practice — claude-code#36682 — so this deserves a real end-to-end check, not an assumption.

What the workspace tells the agent

The creation message says the workspace spans several folders rather than leaving the agent to discover it. Alongside it, a manifest at <root>/.superset/workspace.json and SUPERSET_WORKSPACE_REPOS in the environment list the folders, their repos and their branches. One trap worth naming in that message: git status at the container fails, because the container is not a repo. The agent has to be in a folder.

A dropdown at the top of the right-hand pane listing the workspace's folders with a check on the active one, exactly as in Codex. Selecting a folder re-roots the file tree and the Changes list below it. Dirty counts per folder belong on the rows so you can see where the work is without opening each one.

The client side is small

The file tree derives its root from a single expression — const rootPath = workspaceQuery.data?.worktreePath ?? "" in the v2 FilesTab. The picker replaces that one expression with the selected folder's path.

v2-workspace/$workspaceId/.../FilesTab/FilesTab.tsx:92

The server side is not

The v2 workspace surface reads git through workspaceTrpc.git.getStatus({ workspaceId }) — the host-service router, keyed by workspace id. So the picker needs, for every workspace and not only remote ones:

  • An optional repo argument on the git procedures, resolved through the one 31-line resolveWorktreePath that all 24 call sites share. Omitting it keeps returning the primary, so nothing existing changes.
  • The status store re-keyed from workspaceId → baseBranch to include the folder. Three repos in one workspace usually share a base branch name, so today they would collide on one key and the last snapshot would win — showing one repo's diff under another's name.
  • The refresh limiter re-keyed the same way, or the repos serialise behind one active slot.
  • N file watchers per workspace instead of one, with refcounting, or edits outside the primary never mark the workspace dirty.

Correcting an earlier version of this page. It claimed the desktop's changes router is path-based end to end and that the picker was therefore nearly free for local workspaces. That router is path-based — but it belongs to the v1 surface. The v2 workspace, which is the one being built on, goes through the host-service git router keyed by workspace id. The re-keying work above is required for local workspaces too, not deferred with cloud.

State

The selected folder is per workspace, which is entity-keyed with unbounded cardinality — so per the desktop's persisted-state policy it belongs in host-side SQLite, not localStorage.

Yes — one PR per folder, and the schema is already there

workspace_pull_requests is already a many-to-many join, primary-keyed on (workspace_id, pull_request_id), and its own comment says "a workspace that opens a PR per branch accumulates one row each." Each pull_requests row already carries project_id, repo_owner and repo_name, so a PR already knows which repo it belongs to.

So per-folder PRs need no schema change at all. workspaces.pull_request_id stays what it is — the single "currently linked" pointer the legacy sidebar reads — and keeps pointing at the primary's PR. What changes is the UI that reads the join instead of the pointer, and createForWorkspace taking a folder so it resolves the right checkout and base.

Surfaces that do not change

Worth stating, because it is most of the app. Panes, tabs, the editor, the terminal, file read/write, attachments and search all take an absolute path already and never ask which repo it came from. Automations need nothing: they target a project, and the project now carries the list. The cloud database is untouched in v1.

The decision this forces

Is "the workspace" singular or plural in the header? Item 3 is the one place the model leaks into a surface that has no obvious answer. The branch name and dirty indicator are workspace-level today. With N folders they can either follow the picker — making the header a view of the selected folder — or aggregate, showing a count and the worst status.

Following the picker is more consistent and much cheaper. Aggregating tells you more at a glance but invents a summary the git model has no concept of. Worth deciding before the picker is built, because it determines whether the selection is pane-local state or workspace-level state.

Build order

Four steps, each shippable, each useful on its own.

  1. The host primitive

    workspace_repos, root_path, the creation loop, atomic rollback, delete-all, and the backfill. Driven by a repeatable --project on the CLI and a repos array in ws get. No UI at all. Dogfoodable from a terminal on day one.

  2. Project v2 behind the flag

    project_folders, the Source folders list in the project form, and the workspace composer summarising the folders it will check out.

  3. Agent context

    Primary as cwd, secondaries as additional directories, CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD, the manifest, the environment variable, and the creation message. Verified end to end against a real agent, because the permission behaviour here is the part most likely to surprise us.

  4. The folder picker

    Changes and Files re-rooted by selection, with per-folder dirty counts. The client change is one expression per pane; the real work is server-side and applies to every workspace — an optional repo argument through resolveWorktreePath, the status store and refresh limiter re-keyed to include the folder, and N file watchers instead of one. This is the largest of the four steps.

Not in v1

Deferred

wanted, later
  • Per-repo Ship and one PR per repo — the branch exists, so this is an increment
  • Cross-linked PR bodies and workspace-name titles
  • Cloud sandboxes: they keep cloning one repo for now. The shape is already designed for them (see The shape) — it is the clone loop and the seed step that are unbuilt, not the model
  • Sidebar grouping by project; a multi-repo workspace files under its primary
  • Per-repo setup scripts

Deleted, not deferred

the picker over local projects removes these
  • A GitHub App "Add repositories" dialog with search, avatars and access states
  • Per-repository installation tokens — the folders are already cloned on the machine
  • Merged "all repositories" diff. One folder at a time, by selection
  • Per-folder branch names inside one workspace

Open questions

  1. Cap on folders per project. Eight is the PRD's number, chosen for sandbox disk and creation time. Nothing enforces it structurally and raising it is one line — but a cap that exists is easier to raise than one that never existed.
  2. Does the picker belong in the header too? The right pane is the obvious home. Whether the workspace header should mirror the selection, or stay workspace-level, decides whether "which folder am I in" is a pane concept or a workspace concept.
  3. What happens when a folder's repo is removed from the project? Existing workspaces keep it, per the PRD. Worth confirming that reads as intended rather than as a bug when the folder is still on disk.
  4. Additional-directory permissions. Whether a secondary worktree is writable by the agent without per-call approval is the one behaviour here that has burned another vendor. This is a thing to verify early, not late.
